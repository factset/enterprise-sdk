# Conversational client library for .NET

[![API Version](https://img.shields.io/badge/api-v0.2.0-blue)](https://developer.factset.com/api-catalog/conversational-api)
[![Nuget](https://img.shields.io/badge/nuget-v0.0.1-orange)](https://www.nuget.org/packages/FactSet.SDK.Conversational/0.0.1)
[![Apache-2 license](https://img.shields.io/badge/license-Apache2-brightgreen.svg)](https://www.apache.org/licenses/LICENSE-2.0)

This API lets you send a question to FactSet's 
conversational agent and get an answer back, formatted the same
way OpenAI's Chat Completions API formats its responses. That
means tools already built to talk to OpenAI-style chat APIs (chat
UIs, IDE assistants, evaluation harnesses, and so on) can talk to
conversational agent with little or no changes.

A few things work a bit differently from a typical OpenAI
integration:

- Even though you can send a full list of messages (a \"chat
  history\"), only the most recent message from the user is
  actually used as the question being asked. Any earlier
  messages, or a system prompt, are ignored.
- Instead, the API keeps track of the conversation for you. Each
  conversation has an id (`conversation_id`). Send that id back on
  your next request and the assistant will remember what was said
  before and continue the same conversation. Leave it out and a
  new conversation is started, with a fresh id handed back to you
  to reuse next time.
- The answer isn't returned all at once — it's streamed back a
  little at a time as it's generated, using a format called
  Server-Sent Events (`text/event-stream`). This is the same
  streaming format OpenAI's API uses, so most existing client
  libraries already know how to read it. The stream always ends
  with a `data: [DONE]` line so the client knows there's nothing
  more coming.

**A note on FactSet's internal API standards:** this endpoint's
contract is intentionally OpenAI's Chat Completions API contract,
not FactSet's own API design standards — that's the entire point
of the endpoint, since it lets existing OpenAI-compatible clients
work against it unmodified. Where the two disagree, OpenAI's
contract wins by design, and the FactSet standard does not apply.
In particular:

- Member names (`finish_reason`, `reasoning_content`,
  `factset_configuration`, `conversation_id`,
  `return_raw_link_context`, `factset_context`) are snake_case,
  matching OpenAI's own field naming (and, for
  `reasoning_content`, DeepSeek's), rather than FactSet's
  camelCase convention.
- Error responses are plain text, matching this service's shared
  error-handling framework, rather than FactSet's structured
  `{\"errors\": [...]}` JSON envelope.
